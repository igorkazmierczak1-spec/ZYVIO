WAŻNE:
Najpierw przeanalizuj istniejący projekt, architekturę, Clerk, PostgreSQL, role USER/ADMIN, API oraz obecny panel ADMIN. NIE usuwaj ani nie psuj istniejących funkcji. Zachowaj obecne uwierzytelnianie Clerk i istniejące zabezpieczenia.

Nie twórz fikcyjnych płatności, przychodów, subskrypcji ani danych. Wszystko, co pokazuje panel, musi pochodzić z rzeczywistych danych Stripe lub lokalnej bazy.

2. STRIPE

Zintegruj VYBE ze Stripe w sposób produkcyjny.

Użyj Stripe Checkout oraz Stripe Billing/Subscriptions zgodnie z najlepszym rozwiązaniem dla obecnej architektury.

NIE umieszczaj kluczy Stripe w frontendzie.

Sekrety Stripe mają być przechowywane wyłącznie jako Replit Secrets/environment variables.

Przygotuj konfigurację:

STRIPE_SECRET_KEY
STRIPE_WEBHOOK_SECRET
STRIPE_PREMIUM_MONTHLY_PRICE_ID
STRIPE_PREMIUM_YEARLY_PRICE_ID

Jeżeli Stripe nie jest jeszcze skonfigurowany, przygotuj integrację tak, aby po dodaniu tych sekretów można było ją uruchomić bez przepisywania systemu.

==================================================
3. CHECKOUT

Po kliknięciu „Kup Premium”:

1. Sprawdź zalogowanie przez Clerk.
2. Pobierz prawdziwy identyfikator użytkownika Clerk.
3. Znajdź lub utwórz powiązany profil VYBE.
4. Utwórz/pobierz Customer w Stripe.
5. Utwórz Stripe Checkout Session.
6. Przekieruj użytkownika do bezpiecznego Checkout Stripe.
7. Po udanej płatności wróć do VYBE.

Nigdy nie ufaj frontendowi w kwestii:

- ceny,
- statusu Premium,
- identyfikatora użytkownika,
- uprawnień.

Wszystko musi być potwierdzane po stronie serwera.

==================================================
4. WEBHOOK STRIPE

Dodaj bezpieczny endpoint webhook Stripe.

Obsłuż odpowiednie zdarzenia związane z subskrypcją, w szczególności:

- checkout.session.completed,
- customer.subscription.created,
- customer.subscription.updated,
- customer.subscription.deleted,
- invoice.paid,
- invoice.payment_failed.

Weryfikuj podpis webhooka Stripe.

Webhook musi być odporny na wielokrotne otrzymanie tego samego eventu.

Nie aktywuj Premium wyłącznie na podstawie powrotu użytkownika z Checkout.

Premium ma być aktywowane na podstawie zweryfikowanych danych Stripe.

16. BEZPIECZEŃSTWO

Szczególnie dopilnuj:

- Stripe secret key tylko backend,
- webhook signature verification,
- brak możliwości zmiany Premium przez frontend,
- brak możliwości zmiany ceny przez frontend,
- brak zaufania do userId przesłanego przez klienta,
- używanie Clerk session jako źródła tożsamości,
- ADMIN endpoints zabezpieczone istniejącym requireAdmin,
- Premium endpoints zabezpieczone requirePremium,
- walidacja danych wejściowych,
- ochrona przed replay/double webhook events,
- bezpieczne logowanie błędów,
- brak sekretów w logach.

18. TESTY

Po implementacji wykonaj testy:

1. USER bez Premium nie może korzystać z funkcji Premium.
2. USER z aktywnym Premium ma dostęp.
3. Wylogowany użytkownik nie może rozpocząć chronionego procesu.
4. USER nie może nadać sobie Premium requestem.
5. USER nie może zmienić ceny.
6. USER nie może podszyć się pod innego użytkownika.
7. ADMIN ma dostęp do panelu monetyzacji.
8. Zwykły USER nie ma dostępu do /api/admin/billing.
9. Webhook Stripe odrzuca nieprawidłowy podpis.
10. Ten sam webhook przetworzony drugi raz nie powoduje podwójnego efektu.
11. Anulowanie subskrypcji poprawnie aktualizuje status.
12. Nieudana płatność poprawnie aktualizuje status.
13. Stripe Customer Portal działa.
14. Brak konfiguracji Stripe nie powoduje crashu całej aplikacji.
15. Typecheck frontend/backend.
16. Test produkcyjnego buildu.
